# 错误恢复层精准化设计方案

## 现状诊断（两个根因）

1. **错误链在 Registry 边界被拍扁**。各工具用 `%w` 规范地包装了 OS 错误，但 `DefaultRegistry.Execute`（`internal/tools/types.go:125`）用 `%v` 把 error 渲染成字符串塞进 `Output`，error 值本身被丢弃。下游 `RecoveryManager` 拿到的只剩文本，`errors.Is/As` 无法跨越边界——这才是被迫用 `strings.Contains` 匹配的根因。
2. **bash 分支是死代码**。bash 工具遵循自愈设计（`bash_executor.go:93-99`），命令失败时返回 `(文本, nil)`，`IsError` 永远为 false；而 `loop.go:271` 只在 `IsError=true` 时调用 `AnalyzeAndInject`，所以 recovery.go 里 `command not found`/`超时`/`syntax error` 三个提示从未生效过。

## 设计总览

你提出的两个方向不是二选一，而是互补的两层：

- **POSIX 哨兵错误分类** = 在错误**产生处**（工具内部，error 值还活着时）用 `errors.Is(err, fs.ErrNotExist)` / `errors.Is(err, fs.ErrPermission)` 精准分类。这比匹配 POSIX 错误**文本**更精准——完全不受 locale、文案包装影响，且天然穿透 `%w` 链。
- **领域错误码** = 把分类结果以**结构化数据**形式跨越 Registry 边界传输（`ToolCallResult.ErrorCode`），recovery 层只按码查表，零字符串匹配。

bash 特殊处理：命令失败没有 Go error 可用（自愈设计不能破坏），引入 **Soft Failure** 概念——bash 返回携带错误码的 `*ToolError` 但标记 `Soft: true`，Registry 提取码后仍置 `IsError=false`，输出原样回传给模型自纠，同时 recovery 层可以按码注入提示（让现有死提示生效）。bash 的分类信号本身也是精准的：超时用 `timeoutCtx.Err()`（非字符串），command not found 用**退出码 127**（非 stderr 文本）；仅 syntax error 保留对 stderr 的 best-effort 文本匹配（bash 退出码 2 语义太宽泛，无法区分）。

## 分层改动

### 1. `internal/schema/tool_error.go`（新增）——错误码契约层

放 `schema` 而非 `tools`：`tools` 已导入 `context`（skill_reader.go:8），`context`（recovery 所在包）不能反向导入 `tools`，`schema` 是双方共同依赖的契约层。

```go
type ToolErrorCode string

const (
    ErrCodeToolNotFound     ToolErrorCode = "ERR_TOOL_NOT_FOUND"      // 模型幻觉调用了未注册工具
    ErrCodeInvalidArgs      ToolErrorCode = "ERR_INVALID_ARGS"        // JSON 参数解析失败
    ErrCodePathEscape       ToolErrorCode = "ERR_PATH_ESCAPE"         // 路径逃逸出工作区
    ErrCodeNoWorkspace      ToolErrorCode = "ERR_NO_WORKSPACE"        // ctx 缺少工作区
    ErrCodeFileNotFound     ToolErrorCode = "ERR_FILE_NOT_FOUND"      // POSIX ENOENT
    ErrCodePermissionDenied ToolErrorCode = "ERR_PERMISSION_DENIED"   // POSIX EACCES/EPERM
    ErrCodeIOFailure        ToolErrorCode = "ERR_IO_FAILURE"          // 其他 OS/IO 错误兜底
    ErrCodeEditNoMatch      ToolErrorCode = "ERR_EDIT_NO_MATCH"       // oldContent 无匹配
    ErrCodeEditAmbiguous    ToolErrorCode = "ERR_EDIT_AMBIGUOUS"      // oldContent 多处匹配
    ErrCodeCmdTimeout       ToolErrorCode = "ERR_CMD_TIMEOUT"         // bash 超时强杀
    ErrCodeCmdNotFound      ToolErrorCode = "ERR_CMD_NOT_FOUND"       // bash 退出码 127
    ErrCodeCmdFailed        ToolErrorCode = "ERR_CMD_FAILED"          // bash 其他非零退出
    ErrCodeUnknown          ToolErrorCode = "ERR_UNKNOWN"             // 未分类的外来 error
)
```

`schema.ToolCallResult`（`schema/types.go:38-42`）增加字段：`ErrorCode string \`json:"errorCode,omitempty"\``（omitempty，不破坏现有 JSON 序列化）。

### 2. `internal/tools/errors.go`（新增）——ToolError 类型 + POSIX 分类器

```go
// ToolError 工具领域错误。Code 供程序匹配；Msg 面向模型可读；Cause 保留底层错误链。
type ToolError struct {
    Code  schema.ToolErrorCode
    Msg   string
    Cause error
    Soft  bool // Soft=true 表示软失败（如 bash 命令失败）：输出照常回传模型自纠，不标记 IsError
}
func (e *ToolError) Error() string  // "[CODE] Msg: cause"
func (e *ToolError) Unwrap() error  // 返回 Cause，保留 errors.Is 穿透能力

// wrapSysError 用 POSIX 哨兵分类 OS 错误——errors.Is 而非字符串匹配。
// ENOENT → ERR_FILE_NOT_FOUND; EACCES/EPERM → ERR_PERMISSION_DENIED; 其他 → ERR_IO_FAILURE
func wrapSysError(prefix string, err error) *ToolError
```

### 3. 各工具改造（产生处分类）

- `file_reader.go`：L48-50 → NoWorkspace；L54-56 → InvalidArgs；L58-60 → PathEscape；L62-65/L70-73/L78-81 三处 OS 错误 → `wrapSysError`
- `file_writer.go`：同样模式（MkdirAll/WriteFile → `wrapSysError`，解析/路径检查 → 对应码）
- `file_editor.go`：L124、L193（多处匹配）→ EditAmbiguous；L158、L189（无匹配）→ EditNoMatch；L75/83/92/104 OS 错误 → `wrapSysError`；L66/70 → InvalidArgs/PathEscape
- `bash_executor.go`：
  - 超时分支 L88-91：改为返回 `&ToolError{Code: ErrCodeCmdTimeout, Msg: 原输出文本, Soft: true}`（`timeoutCtx.Err() == context.DeadlineExceeded` 判定，非字符串）
  - 失败分支 L97-99：`cmd.ProcessState.ExitCode()` 判定——127 → ErrCodeCmdNotFound（Soft）；stderr 含 `syntax error` → 保留码但标注 best-effort（bash 退出码 2 语义太宽，这是全方案唯一保留的文本匹配，且匹配的是 shell 固定输出）；其余 → ErrCodeCmdFailed（Soft，无提示，信任模型自纠）

### 4. `internal/tools/types.go` Registry——提取码并传输

`Execute`（L105-135）改造：
- 未注册工具（L113-118）→ `ErrorCode: ERR_TOOL_NOT_FOUND`
- `err != nil` 时 `errors.As(err, &te)`：
  - 命中且 `te.Soft` → `IsError: false, Output: te.Msg, ErrorCode: te.Code`（保住 bash 自愈语义）
  - 命中硬错误 → `IsError: true, Output: "[CODE] 工具 x 执行失败: ...", ErrorCode: te.Code`（模型可直接看到稳定 token）
  - 未命中（外来 error）→ `ErrorCode: ERR_UNKNOWN`

### 5. `internal/engine/loop.go`——放宽注入触发条件

`loop.go:270-280`：`if result.IsError` → `if result.IsError || result.ErrorCode != ""`，并把码传给 recovery。这样 bash 软失败（IsError=false 但带码）也能命中提示。

### 6. `internal/context/recovery.go`——重写为纯码表驱动

```go
var recoveryHints = map[schema.ToolErrorCode]string{

    schema.ErrCodePermissionDenied: "...工作区权限提示（原文案保留）...",
    schema.ErrCodeEditNoMatch:      "...file_reader 重读文件提示（原文案保留）...",
    schema.ErrCodeEditAmbiguous:    "...增加上下文确保唯一性提示（原文案保留）...",
    schema.ErrCodeCmdNotFound:      "...替代命令/先安装提示（原文案保留）...",
    schema.ErrCodeCmdTimeout:       "...nohup 转后台提示（原文案保留）...",
}

func (m *RecoveryManager) AnalyzeAndInject(toolName string, code schema.ToolErrorCode, rawOutput string) string
```

- 全部 `strings.Contains` / `strings.ToLower` 删除；按工具名的 switch 删除（错误码本身已含语义，跨工具通用）；`toolName` 参数保留给日志与 `ERR_TOOL_NOT_FOUND` 提示。
- 未命中码 → 原样返回（与现状一致）。

## 行为变化说明（非回归，需知悉）

1. bash 超时 / command-not-found 的自救提示从「永不触发」变为「正常触发」——这是修复死代码，不是语义改变。
2. 硬错误的模型可见输出会多一个 `[ERR_XXX]` 前缀 token，给模型一个稳定的自纠信号。
3. `AnalyzeAndInject` 签名变更，唯一调用方 loop.go 同步修改。
